XÂY DỰNG HỆ THỐNG MICROSERVICES QUẢN LÝ VẬN ĐƠN  1. Mục tiêu 2.  N ghiệp vụ Công ty logistics cần xây dựng một hệ thống Mini Waybill Platform phục vụ tạo và theo dõi vận đơn. Khi khách hàng tạo vận đơn, hệ thống chỉ cần xác thực dữ liệu quan trọng và ghi nhận vận đơn nhanh. Các bước như phân tuyến, khởi tạo tracking, gửi thông báo và ghi audit được xử lý bất đồng bộ thông qua Kafka. Yêu cầu chính: luồng tạo vận đơn không được gọi tuần tự tất cả service bằng REST. Phần lớn hậu xử lý phải được kích hoạt bởi event Kafka. 3. Chi tiết từng Microservice 5.1. Customer Service Quản lý thông tin khách hàng gửi hàng. Cung cấp API kiểm tra customer tồn tại và đang ACTIVE. Có database/schema riêng. Customer - id - customerCode - fullName - phone - email - status - createdAt POST /customers GET  /customers/{id} GET  /customers/{id}/validation 5.2. Shipment Service Nhận request tạo vận đơn từ API Gateway. Kiểm tra requestId/idempotency key trong Redis để chống tạo trùng. Dùng OpenFeign gọi Customer Service xác minh người gửi. Lưu Shipment ở trạng thái CREATED/PENDING_ROUTING. Publish SHIPMENT_CREATED lên Kafka sau khi ghi DB thành công. Không gọi trực tiếp Routing, Tracking, Notification hoặc Audit bằng REST trong luồng tạo vận đơn. Shipment - id - trackingCode - customerId - senderName / senderPhone / senderAddress - receiverName / receiverPhone / receiverAddress - serviceType - weight - codAmount - currentStatus - createdAt POST /shipments GET  /shipments/{trackingCode} GET  /shipments?customerId={customerId} 5.3. Routing Service Consume SHIPMENT_CREATED. Mô phỏng phân tuyến dựa trên tỉnh/thành hoặc warehouse code. Lưu Route Assignment vào DB riêng. Publish ROUTE_ASSIGNED khi tính tuyến thành công. Nếu xử lý lỗi tạm thời, phải retry; quá số lần retry thì đẩy sang DLT/DLQ. RouteAssignment - id - trackingCode - sourceHub - destinationHub - routeCode - status - assignedAt 5.4. Tracking Service Consume SHIPMENT_CREATED, ROUTE_ASSIGNED và các TRACKING_UPDATED event. Lưu timeline trạng thái của vận đơn. Cập nhật Redis key shipment-status:{trackingCode} để client query nhanh. Cung cấp API đọc current status + lịch sử tracking. TrackingHistory - id - trackingCode - status - locationCode - note - occurredAt GET /tracking/{trackingCode} GET /tracking/{trackingCode}/history 5.5. Notification Service Consume các event quan trọng: SHIPMENT_CREATED, ROUTE_ASSIGNED, DELIVERED, DELIVERY_FAILED. Không được Shipment Service gọi trực tiếp bằng REST trong luồng chính. Mô phỏng gửi SMS/email bằng log hoặc lưu Notification DB. Consumer phải idempotent, không gửi trùng notification nếu event bị redelivery. 5.6. Audit Service Consume toàn bộ business event quan trọng. Lưu eventId, eventType, trackingCode, payload tóm tắt, occurredAt. Dùng để tra soát lịch sử hệ thống, không tham gia vào luồng nghiệp vụ đồng bộ. 13. Xử lý lỗi bắt buộc Error code / tình huống Cách xử lý mong đợi CUSTOMER_NOT_FOUND Reject create shipment; không publish SHIPMENT_CREATED DUPLICATE_REQUEST Không tạo shipment lần hai; trả kết quả phù hợp DEPENDENCY_SERVICE_UNAVAILABLE Feign timeout/fail rõ ràng; không treo request KAFKA_TEMPORARY_ERROR Có cơ chế retry/publish an toàn; nêu rõ giới hạn của cách làm DUPLICATE_EVENT Consumer idempotent, không tạo dữ liệu/notification trùng POISON_MESSAGE Retry hữu hạn rồi chuyển DLT/DLQ OUT_OF_ORDER_EVENT Giải thích cách dùng trackingCode làm key và/hoặc kiểm tra transition status 14. Quy tắc chuyển trạng thái vận đơn CREATED   -> PENDING_ROUTING   -> ROUTE_ASSIGNED   -> PICKED_UP   -> IN_TRANSIT   -> OUT_FOR_DELIVERY   -> DELIVERED OUT_FOR_DELIVERY -> DELIVERY_FAILED -> OUT_FOR_DELIVERY (retry) Không cho phép trạng thái lùi bất hợp lý, ví dụ DELIVERED -> IN_TRANSIT. Tracking Service phải validate transition hoặc lưu version/sequence để tránh event cũ ghi đè trạng thái mới.
