# Security, CSKH chat, and AI rollout

The repository changes cover account registration, session revocation, ticket capabilities, object access, WebSocket authorization/reconnection, a transactional chat outbox, private attachments, shipment pagination, and AI token streaming with session memory. These instructions do not claim that production has already been updated.

## Compatibility and preparation

- All existing JWTs must be replaced by logging in again. New tokens contain per-user and per-role versions checked against Redis. Missing Redis state fails closed. Password changes and permission/station changes invalidate old sessions.
- A pending revocation marker blocks sessions during a permission update. If Redis fails after the database commits, the marker remains until the old token lifetime expires. After repairing Redis, reconcile the current database permissions, advance the matching version and remove the pending marker; do not just clear it while old tokens remain valid.
- New anonymous tickets receive a random `accessToken` once at creation. The browser retains it in session storage and displays it for recovery on another device. Existing anonymous tickets have no capability; staff must verify the customer before migrating/reissuing access. Knowing a ticket code no longer grants access.
- Attachments become private. Uploads require `ticketId` and ticket access. Responses contain an object key and a ten-minute signed preview URL. A ticket read refreshes signed URLs. Configure `MINIO_PUBLIC_URL` to the externally reachable S3 origin, with no path prefix; proxying must preserve Host/path for S3 signatures. Legacy URLs stored in existing messages are re-signed for authorized readers.
- Flyway adds `guest_access_hash` and `support_chat_outbox`. Take a database backup before the rollout. Retain the new tables/column when rolling back binaries; do not delete pending outbox rows.
- `GET /api/shipments/page` supports page/size, customer, keyword and status. The shipment list uses database pagination and scope-wide aggregate statistics. Legacy operational projection endpoints remain compatible; migrate those consumers separately before claiming large-data capacity.

## Runtime secrets and database login

Run `scripts/prepare-runtime-secrets.ps1` to create ignored files under `.secrets/`. It refuses to overwrite existing files and never prints values. The files are templates for a fresh deployment, not a command to rotate an existing installation blindly.

For an existing installation:

1. Preserve the current SQL administrator password as `db-admin-password` until `ALTER LOGIN sa` is performed deliberately. Changing a container environment variable does not rotate a login in an existing database volume.
2. Use an administrator connection to run `database/security/provision-app-login.sql` with the generated application password. It creates/updates `waybill_app` in the application databases with reader/writer/DDL permissions needed by JPA/Flyway, without SQL Server sysadmin privileges. Use passwords generated by the preparation script; never interpolate arbitrary unescaped values into SQLCMD variables. A separate login per service is a later isolation improvement.
3. Put `db-user=waybill_app` and its password into `db-password`. Runtime manifests now use these application credentials, while SQL bootstrap uses `db-admin-password`.
4. Coordinate Redis authentication with all Redis clients. Populate `redis-password` before applying the new server/client manifests. For JWT, deploy the same new key to auth, gateway and notification services. Log in again after the rollout.
5. Rotate RabbitMQ and MinIO persisted identities through their administration tools before switching clients. RabbitMQ's default-user settings do not change an existing user. Retain existing storage and object data. Fill real mail credentials; empty generated mail fields are not a working mail configuration.
6. Apply the runtime secret from the private file; avoid printing or committing its contents. Both deployment scripts now use an env file instead of known default passwords. Check the target kube context before applying anything.

Docker Compose binds internal ports to loopback and requires the ignored env file. It targets local development; expose production through authenticated ingress/TLS rather than reopening these ports.

## Deployment order

1. Confirm a healthy backup and record existing image tags/configuration for rollback. Prepare the required runtime secret keys and the application database login first.
2. Build/version the changed service images and frontend. Existing checked-in image tags still refer to the previous images; update them to the images actually built before deploying.
3. Deploy support-service so Flyway creates V2/V3, followed by auth, gateway, payment, shipment, routing, tracking, notification and frontend. Coordinate the JWT rollout in a maintenance window. Do not claim uninterrupted access during secret/session changes.
4. Apply the ingress WebSocket path and network policies. The most specific `/api/notifications/ws` path goes directly to notification-service:8085; HTTP business APIs remain behind gateway. Docker Nginx has the corresponding Upgrade route.
5. Verify the ingress controller labels and CNI NetworkPolicy support. The checked-in exception targets Traefik in `kube-system`. An ingress-nginx deployment requires an explicit namespace/pod-selector exception. Prometheus in `waybill` can scrape backends. Internal services trust gateway-generated identity headers inside this restricted network; this is not mTLS authentication between services.
6. `TRUSTED_PROXY_REGEX` must match only the real ingress proxy addresses. The manifest uses the k3s default pod CIDR. Keep gateway ports private and ensure ingress overwrites/appends forwarded IPs correctly.

## Acceptance checks

Local verification on 2026-10-14 completed successfully: the full Maven reactor packaged with 104 backend tests passing, and both frontend chat tests passed. The local WebSocket transport test uses two real client sessions against an embedded server; shipment pagination tests execute against H2. Docker Compose configuration and Kubernetes Kustomize rendering also passed. Infrastructure-dependent `*ApplicationTests` were excluded (`mvn package '-Dtest=!*ApplicationTests' '-Dsurefire.failIfNoSpecifiedTests=false'`), so these results do not establish production SQL Server migration compatibility or production ingress performance. Complete the deployment checks below on the actual environment.

- Registering an existing Google email cannot set a password or issue its token. Direct admin requests without a valid admin JWT fail.
- Customer A cannot read B's payment/ticket, post into B's ticket, or confirm COD/configure the scheduler. An anonymous ticket requires its own capability for HTTP, uploads and WebSocket subscriptions.
- Changing a role, permission, station or password invalidates earlier HTTP tokens and private WebSocket delivery. Test a Redis restart/state loss: old sessions must fail closed and a fresh login must work.
- Anonymous tracking contains no addresses, phones, staff identifiers or free-text internal notes. Direct object URLs without a valid signature fail.
- On the real domain, the WebSocket handshake returns 101. Two browser sessions receive chat messages; disconnect/reconnect and ticket switching do not lose or duplicate messages. With Kafka temporarily unavailable, committed messages remain in the outbox and are delivered when Kafka returns.
- Search/status/customer filters apply across all pages. No page exposes another customer's shipments. Statistics remain scope-wide rather than reflecting only the current page.
- Observe API 401/403/429/502, Redis errors, pending outbox count/age, CPU/memory and SQL storage. Verify `kubectl top pods` and PVC free space before setting capacity targets.

## Rollback and remaining limits

Roll back application image tags and ingress routes together. Restore matching runtime credentials only if the corresponding server/database identity still accepts them; otherwise repair credential alignment. Keep new schema and pending outbox data. Do not restore public attachment access or the Google-registration takeover behavior.

The chat outbox offers at-least-once delivery; frontend deduplicates by message ID. Notification currently uses one in-process broker replica. Before scaling notification horizontally, add shared fan-out for ticket/payment/trip events and sticky SockJS sessions or an external broker; existing Redis tracking fan-out alone does not cover ticket chat.

AI tool access has been secured: ticket lookup no longer dumps private customer descriptions, and waybill lookup masks receiver names and addresses. AI responses stream token-by-token over SSE (`/api/support/ai/stream`) with a 10-message session memory window and an empirical Ollama CPU benchmark endpoint (`/api/support/ai/benchmark`).
